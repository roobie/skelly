# Controls and input ownership

Read with [INTERFACE.md](INTERFACE.md), especially “Text” and
“Combat and feedback”. The binding registry is authoritative for gameplay chords and their displayed labels. Character-screen tabs and the Items layout are in [inventory-layout](docs/inventory-layout.md).

## Ownership

A visible context owns attention: menus, reading, inventory and debug modals shield gameplay even if no widget consumes a key. Availability, reach, ammunition and refusal remain with gameplay owners. See `packages/presentation/src/presentation/inputBindings.ts`, `KeyboardInput`, and `packages/presentation/src/presentation/play.ts`, `startPlay`.

The browser keeps native text entry, IME, selection, clipboard and focus traversal. Deadvox does not duplicate a text editor or browser focus engine. The binding registry refuses Ctrl, Cmd/Meta and Alt as chord modifiers, so those chords are never game actions. A plain Alt key may own a held action: free look needs its physical edges without turning browser shortcuts into bindings. Play cancels both Alt edges because browser menu activation can occur on release. This is page-level cancellation, not a guarantee against desktop interception. While playing (pointer locked, no text field focused) the game owns the keyboard and cancels every such chord the page receives, because a stray Ctrl+U or Ctrl+S mid-fight opens a browser window and costs the player the run. Menus and text fields keep native behaviour. No page can cancel Ctrl+W, Ctrl+T or Ctrl+N by default: Chromium delivers them only under the Keyboard Lock API, which works only in page-requested fullscreen. So fullscreen is an opt-in button in the options, and the lock applies only while the page holds fullscreen; where the API is missing (Firefox, Safari) fullscreen still works and those chords stay with the browser. The lock leaves Escape out so a tap still frees the pointer, and the option is not remembered because the browser needs a fresh click to enter fullscreen. See `packages/presentation/src/ui/fullscreenOptions.ts`, `syncKeyboardLock`. Synthetic events do not prove immunity from desktop interception. See `packages/presentation/src/presentation/inputBindings.ts`, `KeyboardInput`, `install`. In pointer-locked menus, the drawn cursor handles controls that native pointer lock cannot operate, such as range dragging.

Physical key positions define bindings; labels follow the browser's keyboard layout. A modifier's own physical edge takes precedence over its aggregate flag because inconsistent edge flags must not disable unrelated movement. Browser chrome can swallow Alt and movement releases without delivering blur or pointer-lock loss. A later keyboard or pointer event that reports Alt up contradicts a retained Alt hold, so the game forgets all held ownership, including movement; a fresh press can resume without a missing release blocking it. Window focus return also forgets held ownership because the corresponding blur may be missing. Each frame checks document focus, visibility and pointer lock rather than relying only on lifecycle events. Ordinary physical keys cannot be polled, so missing releases with no contradicting signal cannot be inferred from silence or a timer. This does not authorize reconstructing other missing key events. See `packages/presentation/src/presentation/inputBindings.ts`, `KeyboardInput.reconcileFocus` and `KeyboardInput.install`. Rebinding must consider alternate bindings and held gates so a hidden conflict cannot steal movement or run two actions. See `packages/presentation/src/presentation/inputBindings.ts`, `KeyboardInput`, and `packages/engine/src/game/bindingRegistry.ts`, `BindingRegistry` and `bindingConflict`.

When the window loses focus or the page is hidden, held keys are forgotten rather than blocked until release: the release may go to another window, so a block would refuse the key's next press. During binding capture, a mouse press on a page control operates the control rather than becoming the binding, so Cancel, Reset or another row cannot bind the mouse button that pressed it. Under pointer lock the native press lands on the canvas, so the control is the one under the drawn menu cursor, which the menu pointer resolves. A Shift pressed during capture waits for a chord key and is captured alone only on its release, so a Shift chord can be entered. See `packages/presentation/src/presentation/inputBindings.ts`, `KeyboardInput`, `focusLost`, `install`, `pointerTarget` and `capturePress`; and `packages/presentation/src/ui/menuPointer.ts`, `mountMenuPointer`.

The wheel is not a keyboard chord. Menus keep their scroll ownership so aiming cannot steal a pane's input. An open action menu owns it first, stepping the choice as the arrow keys do, because the player holding the menu open has asked to choose. Optic zoom owns it only in ADS with a variable optic: magnification is an aiming adjustment, not a reason to take the wheel outside aiming. Outside a menu the wheel never picks a held action, so a tool's ordinary action cannot silently lose precedence. The arrow keys are fixed like a native list control's, not rebindable actions, because they only act while a menu is open. See `packages/presentation/src/presentation/play.ts`, `stepActionMenu`; `packages/presentation/src/presentation/opticZoom.ts`, `OpticZoom.wheel`; and `packages/presentation/src/ui/menuPointer.ts`, `mountMenuPointer`.

Bindings are origin-local browser-profile preferences, not saved-character or account state. Stored rows are untrusted and invalid entries are dropped rather than becoming controls. The registry receives its preference store and keyboard-layout source from its constructor, so binding data and conflict rules run without a browser; only the browser construction passes `localStorage` and `navigator.keyboard`. See `packages/engine/src/game/bindingRegistry.ts`, `BindingRegistry`, and `packages/presentation/src/presentation/inputBindings.ts`, `createKeyboardInput`.

Default keys remain base-pack content while startup reads only that pack's defaults: accepting another pack's rows would promise behavior that gets ignored. Stored rebindings must win over defaults so content changes do not erase player preferences. Keep one shared action catalogue so authored references and replay agree without importing browser input handling; see `packages/engine/src/core/inputActions.ts`, `INPUT_ACTIONS`. Default-key validation uses the resolver's conflict policy at the CLI boundary rather than bringing browser dependencies into content admission. See `packages/mods/skelly.controls/controls.jsonnet`, `src/cli/controlIssues.ts`, `controlIssues`, and `packages/engine/src/game/bindingRegistry.ts`, `defaultKeySetIssues`.

## Settled controls

- **Free look** lets the player move one way and watch another without redirecting the gun. Pressing it in ADS ends ADS and releasing it stays at the hip; ADS is refused while it is held. The reason is in `DESIGN.md`, "Firearms". Look-targeted item actions are refused while it is held; firing keeps the body's bore direction so looking away cannot redirect a shot. Releasing the key returns the view to the body; losing pointer lock or focus clears held input because release may go elsewhere. Head offsets are transient, but input replay records them so the recorded view follows the same look. See `packages/engine/src/game/freeLook.ts`, `FreeLook`, `packages/presentation/src/presentation/input.ts`, `Input`, and `packages/engine/src/game/inputReplay.ts`, `InputReplayRecorder`.
- **Debug authoring** uses the held debug gate. The review map and freeze action use debug bindings; the gate is itself a binding, not a browser modifier. Noclip flight is ungated only while noclip is active so flight can be controlled without occupying another hand. Spawn-menu navigation is modal navigation, not authoring. See `src/product/controls.ts`, `INPUT_BINDINGS`, and `packages/presentation/src/presentation/play.ts`, `toggleReviewMap`.
- **Review map height slice** keys belong to the map page, so no game action is lost while the map has focus. The reason for the slice is in `docs/review-map.md`. See `packages/presentation/src/presentation/mapSliceInput.ts`, `mapSliceKeys`, and `src/siteMapPage.ts`, `sliceKey`.
- **Spectator camera** shows the world as others would see it: the avatar is drawn whole, head included, and the player's own view attachments (first-person arms, held item, held light beam, damage, drug and night-vision effects) stay behind with the avatar. The avatar is fully inert while the camera flies, so looking around changes nothing in the simulation: every avatar-bound command and input is refused, and a throw charge held at the toggle is cancelled, not released. Only the command families that drive the view and the debug tools still work; see `packages/presentation/src/presentation/spectatorCamera.ts`, `DETACHED_COMMAND_PREFIXES`. Flight speed is noclip's. The teleport action moves the avatar under the camera, refuses a spot inside solid terrain and lets a spot in the air fall. See `packages/presentation/src/presentation/spectatorCamera.ts`, `SpectatorCamera`, and `packages/presentation/src/render/playView.ts`, `updateCamera`.
- **Q and E** hold left and right lean in world contexts; inventory uses them for selection in its own context, keeping its keys under the left hand next to WASD without leaning the player. Opposing lean keys cancel. See `src/product/controls.ts`, `INPUT_BINDINGS`, and `packages/engine/src/game/playerControls.ts`, `PlayerControls.intent`. The cover, stance and sprint rules are in `DESIGN.md`, "Character".
- **Inventory gestures** use tap on release before the hold threshold, or hold for the related second verb, matching crouch/prone so there is one gesture grammar rather than a double-tap window. Wield means main hand; hold in offhand means offhand, because player text must name the intended verb rather than blur the two hand roles (`INTERFACE.md`, "Text"). Put-target selection uses the checkbox or the held put action, not C cycling, so there is one selection model. A put-target checkbox keeps keyboard focus without claiming text entry, so choosing a destination cannot disable inventory verbs; see `packages/presentation/src/presentation/inputBindings.ts`, `focusedInventoryBindings`. Without an explicit choice, the nearest container in reach is used. Double-click tries wielding before stowing in the player's inventory; refusal must leave the item where it is rather than redirect it to another destination. See `src/product/controls.ts`, `INPUT_BINDINGS`; `packages/presentation/src/ui/inventoryScreen.ts`, `onInputCommand` and `chooseTarget`; and `packages/engine/src/core/options.ts`, `wieldOrPocket`.
- **Item viewer** follows the view-item binding whether it is a pointer button or a key, so any rebind still opens and closes it, and a left drag on the model always turns it. The reason is in `DESIGN.md`, "Inventory screen". See `packages/presentation/src/ui/itemViewer.ts`, `isViewItemPress`, and `packages/presentation/src/ui/menuPointer.ts`, `mountMenuPointer`.
- **World interaction** keeps the target's normal use on tap, so service actions belong in the existing long-press choice list rather than replacing ordinary use. Shared target choice and inventory handling preserve reach and handling ownership. Choosing a repair pins the identity so later looking cannot change the job. See `packages/engine/src/game/handUse.ts`, `interactionTargetAt`; `packages/presentation/src/presentation/play.ts`, `completeWorldInteraction` and `confirmFurnitureAction`; and `packages/engine/src/game/furnitureActions.ts`, `furnitureActionsFor`.
- **Slinging** needs no separate binding: using ordinary wear and quickbar routes avoids another inventory ownership path. See `packages/engine/src/core/inputActions.ts`, `inventory.wear`, and `packages/engine/src/core/options.ts`, `quickbarPutAway`.
- **Downed bodies** use the same world-interaction tap/hold: tap finishes a body, hold dismembers it. The nearest-target rule applies to bodies and ground items. See `packages/engine/src/core/interactionPick.ts`, `pickInteractionTarget`.
- **The main menu** opens through its menu binding; Escape releases pointer lock during play and toggles the menu after death. Escape is not rebindable. F10 belongs to the browser.
- **Reload, rack, remove** share one rebindable action. Hold selects the fullest carried magazine that fits, even if it has fewer rounds than the fitted magazine. A double press racks; a tap followed by a held press removes a detachable magazine. A single tap does nothing. Classification waits for release or the hold threshold, so a quick double tap and a plain hold do not remove a magazine. A pump racks repeatedly while the reload action remains held. A revolver hold opens the crane, preserves live rounds while clearing cases, and loads loose rounds until release; release finishes the current step and closes the crane. Double press cocks a closed revolver or closes an open crane. Tap-then-hold deliberately dumps the cylinder and leaves it open. See `packages/engine/src/game/reloadInput.ts`, `ReloadInput`, and `packages/engine/src/game/firearmHandling.ts`, `FirearmMechanics`.
- **Rest and sleep** have no dedicated keys. Use eligible furniture through world interaction; Wait is a character-screen button. The alarm's wake hour is a setting, not a sleep key. See `packages/presentation/src/presentation/play.ts`, `startPlay`, and `packages/engine/src/game/rest.ts`, `RestController`.
- **Use items** from the hand or quickbar; inventory activation also requires the item in hand, so opening a screen cannot bypass preparation. An ammunition box is wielded and activated to unpack. See `packages/engine/src/game/primaryAction.ts`, `selectPrimaryAction`, and `packages/engine/src/game/survival.ts`, `activateHeld`.
- **Handedness** is actor identity, not a chord swap or physical-slot migration. See [character-handedness](docs/character-handedness.md).
- **Quickbar tap** takes an item into its capability-directed hand or puts it away; hold uses an available action. It does not provide an alternate route for firearm racking. See `packages/presentation/src/presentation/quickbarInput.ts`, `QuickbarInput`, and `packages/engine/src/game/quickbarActions.ts`, `QuickbarActions`.
- **Primary actions** from either hand are refused while handling is busy. Whether one-handed work leaves the free hand usable remains open for BR's decision.
- **Treatment** uses a wielded treatment item or its held quickbar slot. A tap treats the worst bleeding; choosing a region is a held-menu child list, so the common case costs no extra step. Treatment is a normal-speed action that leaves movement free; bleeding refuses time compression. See `packages/engine/src/game/itemActions.ts`, `defaultItemAction`, and `packages/engine/src/core/body.ts`, `Body.compressionRefusal`.
- **Opening cans** is a held tool action as well as a sealed can action, because activating a prepared tool should use it. The other hand supplies the counterpart; a pocket tool cannot bypass preparation. Competing actions require an explicit choice through the held action menu rather than opportunistically changing a weapon click. A lost opening target refuses instead of becoming a swing. See `packages/engine/src/game/canOpening.ts`, `openingTargetForHand`, `packages/engine/src/game/itemActions.ts`, `ItemActionSelection`, and `packages/engine/src/game/handUse.ts`, `createHandUse`.
- **Lighting** requires the matches or other firestarter in hand. A held igniter can light an eligible object in the other hand; an igniter merely within reach does not qualify.
- **HUD toggle** must not overwrite individual visibility preferences. Retain gesture room for third-person camera and debug-panel actions rather than making them collide. See `packages/engine/src/core/inputActions.ts`, `hud.toggle`, and `packages/presentation/src/presentation/backquoteOrbitGesture.ts`, `BackquoteOrbitGesture`.
- **Worn lights** must not require separate key layouts or cycling for different equipment combinations. A unified request stays predictable when goggles and headlamps coexist. Hand and worn beams affect sight exposure as well as GPU cost, so keep the render pool content-bounded rather than allowing equipment to grow shader work without limit. See `packages/engine/src/game/survival.ts`, `toggleWornLights`, `packages/engine/src/core/lights.ts`, `inventoryLightSources`, `packages/presentation/src/render/flashlight.ts`, `Flashlight`, and `packages/engine/src/core/schema/senses.ts`, `SenseSchema`. Gated debug actions can share a physical key without stealing its ordinary action; see `packages/engine/src/core/inputActions.ts`, "light.worn-toggle".
- **Throw stance** is a toggle; holding through its authored threshold drops one held item without toggling. In stance, hold the primary pointer action to charge and release to throw; the secondary pointer action cancels. The stance remains while either hand is occupied. The reload action does not queue during a charge, so a held throw cannot unexpectedly start firearm handling afterward. See `packages/engine/src/game/throwCharge.ts`, `ThrowCharge`, and `packages/engine/src/game/commandRouter.ts`, `beginItemThrow`.
- **Charged strikes** have no binding of their own: hold the dominant use through a melee swing's wind-up to charge, and release to strike. A tap stays the ordinary strike, and a raised block leaves the charge held. See [charged attacks](docs/charged-attacks.md).
- **Continue** is shared after interruption or a stopped craft.
- **Crouch and prone** share one rebindable key: tap to crouch and hold to lie down or rise. Both actions answer one key so the stance keys stay together and a rebind moves both.
- **Carrying** uses a context because it occupies the hands that conflicting actions would need. Keeping its gestures in the registry preserves shared rebinding, labels and replay. Mutually exclusive modes may use contexts; overlapping states need precedence rather than a context per pair. See `packages/engine/src/core/inputActions.ts`, "carry.turn", and `packages/presentation/src/presentation/play.ts`, `playContext`.

## Remaining questions

- Press-and-hold for every long use remains a direction, not a universal cancellation rule. Do not redesign mouse use as part of rebinding.
- BR decides the default best-pocket destination; the binding registry is authoritative for the configured choice and its displayed behavior.
- Add magazine-check inputs only when their mechanics exist and the full conflict model has been checked.
- Whether matches strike alone remains open for BR.

## Native key diagnostics

Native delivery failures cannot be inferred from synthetic events or movement alone. Opt-in debug tracing keeps event admission and cancellation evidence together without collecting typed text. The bounded diagnostic buffer stays outside saved and replay state so observing a refusal cannot change simulation identity. See `packages/presentation/src/presentation/inputBindings.ts`, `KeyboardInput`, and `src/debug/keyTrace.ts`, `KeyTrace`.

## Replay boundary

Input recording samples control state at player ticks so action order does not depend on browser event timing. Replay must restore any held state that changes simulation or shot resolution; presentation-only selection and scroll position do not belong in replay state. Live play still cancels held input on focus loss. Replay must run without a browser, so its session stash and its recording-cost clock come from the caller; the browser passes `sessionStorage` and `performance`. See `packages/engine/src/game/inputReplay.ts`, `replayStateFingerprint` and `ReplayStash`, and `packages/presentation/src/presentation/play.ts`, `captureReplayStartState`.

A replay must pick and aim the same regardless of frame rate. So hand use, a melee swing and a throw aim and pick from the simulated eye and look, never the drawn view, whose ADS blend advances with real time. The view eye keeps the camera, the interaction highlight and the build-mode click; while that blend runs, the highlight and the hand-use pick can disagree briefly. See `packages/engine/src/game/session.ts`, `playerEye`, and `packages/engine/src/game/handUse.ts`, `createHandUse`.

For the same reason a replay must pick the same regardless of asset load timing. The pick lays piles out from content, as they are drawn once the content's models have loaded, never from which models the renderer has loaded so far. While a model loads, the drawn fallback bundle and the pick can disagree briefly. See `packages/engine/src/game/handUse.ts`, `interactionTargetAt`, and `packages/engine/src/core/pileLayout.ts`, `pileLayout`.
